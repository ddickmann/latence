# Estate prototype: the estate files and the handoff

The code that was prototyped here is the workspace package
[`latence-ontology`](../../../packages/latence-ontology/README.md) (ticket 56): the reader for a
DuckDB mirror and for Unity Catalog, the induction, the ledger, the export and its Turtle, SHACL
and PROV-O files, the lifecycle, drift, erasure, the staged statements and the call into the
proposal writer. Its tests run in `pytest packages` under the repository's gates. What stays
here is what the package is run on, and how:

| File | What it is |
|---|---|
| `estates/vehicles.yaml` | what the engine is told about the vehicle and warranty estate |
| `estates/vehicles.gold.yaml` | the hand-checked list the build is scored against (`latence-ontology score`) |
| `estates/vehicles.classes_answer*.json` | the kept answers of a hosted model to the class prompt |
| `HANDOFF.md` | how to run it with the host application |

```bash
cd ../../.. && uv sync                       # the workspace, the package included
cd .scratch/semantic-sidecar/estate
uv run latence-ontology build --config estates/vehicles.yaml --duckdb <mirror.duckdb> \
    --metric-views <views.txt> --verified <host catalog.yaml> --out out/vehicles
uv run latence-ontology export --out out/vehicles --ui-dir <host ui>/public/data/ontology
uv run latence-ontology propose --config estates/vehicles.yaml --out out/vehicles     # the proposal file for a host
```

The modules, by the package's file names (`packages/latence-ontology/src/latence_ontology/`):

| File | What it does |
|---|---|
| `reader.py` | the interface to a warehouse: objects, declared keys, metric views, one query call |
| `reader_duckdb.py` | that interface over a DuckDB mirror |
| `metric_views.py` | reads metric-view definitions |
| `induce.py` | concepts, relations, value sets, hierarchies, attributes, measure bindings, each with signals and support |
| `ledger.py` | assertions and decisions, append-only; the layer is their replay |
| `export.py` | the `graph-export/3` file; its JSON Schema and the table of codes are in `schemas/` (package data) |
| `lifecycle.py` | the five states of an element (draft, proposed, approved, certified, retired): a reviewer approves in `decisions.jsonl`, the data owner the estate file names (`lifecycle.data_owner`) certifies an approved element in `certifications.jsonl` (`latence-ontology certify`), and the engine approves a kind only under a calibration record that reaches its target (`lifecycle.auto_approve`) |
| `staged.py` | the staged proposal for the catalog's owner (`latence-ontology stage`, `staged-catalog.sql`): an approved key or reference between tables that the catalog does not declare, as an informational constraint statement with the decision it rests on; the engine runs none of it |
| `drift.py` | what changed in the catalog under an element a person decided (renamed, retyped, split, dropped): the old decision stays on the record as stale and is not applied, and the element is a proposal again (`drift` in the export) |
| `erasure.py` | a column that turns sensitive is erased from every file of the build folder, the ledger included, and recorded in `erasures.jsonl` without a value |
| `standards.py` | the SHACL shapes (`ontology.shacl.ttl`: one node shape per concept, proposed constraints deactivated) and the PROV-O provenance (`ontology.prov.ttl`: every element generated by the build and attributed to the engine, a person's decision as an activity of its own) beside the Turtle file |
| `mentions.py` | `build --documents <folder>`: the mentions of the estate's rows in its documents (.txt, .md), each a half-open span linked to the one row it names, or left with its candidates where two rows carry the name |
| `pair_voice.py` | a hosted model's vote on the pairs of records the linker leaves for a person: off unless the estate file switches it on with an egress rule (`link.hosted_model`), only the fields the rule names leave, a cap, each call recorded; the vote decides nothing |
| `proposal.py` | a thin call into the repository's package `latence-proposal-writer` (`packages/latence-proposal-writer`), which writes the proposal file for a host's semantic layer from approved decisions and reads the host's receipt back; the file's shape is that package's `schema/proposal-file.schema.json` |

A person's decisions go into `out/<estate>/decisions.jsonl`, one JSON object per line with
`subject`, `verdict` (`approved` or `rejected`), `by`, and optionally the element's `claim`
(a placement, a class and anything that is to go into a proposal file need it), a `reason`
and `at` (the day of the decision). The next `build` reads them; they survive every rebuild.

## The one seam to a host: the proposal file

What a review approved reaches a host's semantic layer by one file and no other way
(ADR-0070). `propose` writes it as `out/<estate>/proposal.yaml` from the build's
`ontology.json` and `decisions.jsonl`; the host's own tool places it into its library as a
reviewed change and writes a receipt.

- **Two kinds of entry, from approved decisions only.** `spellings`: two values of a value set
  a reviewer called the same (the value more rows carry is kept, the other is its spelling).
  `names`: the names of a master list's records by their key, for a list the estate file
  names under `propose.names` (the export marks each such list that is not seeded
  `"proposal": "names"`, so a host's page offers a decision on it). Each entry says where it goes by a catalog object and a column
  and carries its origin: the element's id, its claim, who approved it and on which day.
- **Links between records.** A link between two records a person approved goes in as a `link`
  entry, in the shape the host's tool reads (its ticket 294), and the file then states
  `format: layer-proposal/2`; a file with no link is version 1, as before. Only where the host
  takes it: no seeded record, two objects, the master list's names in the same file, a linked
  record linked to no other, the statements the person saw. `propose.links: false` in the estate
  file keeps a file at version 1.
- **Never written:** a rejected or undecided element; anything seeded (a seeded list, its
  records, a pair that holds one, a pair of values of a value set a seeded object carries); a
  link the machine accepted and no person approved (one certified on simulated labels is such a
  link); an entry whose decision was made on another
  statement than the build now makes (listed as `stale`); an entry whose decision states no
  claim, or no day. The command prints each approved decision it did not write, with the
  reason.
- **The day of a decision** is `at` on its line (a date, or a timestamp such as the host's
  page writes since its ticket 282). A line without one is written only when the command is
  given the day (`--decided-on YYYY-MM-DD`), which never replaces a day a line states; no day
  is made up.
- **The same inputs give the same bytes.** The file is YAML in block style with every text in
  double quotes.
- **The receipt.** `build --receipt <file>` (repeat for more, oldest first) reads what the
  host wrote when it placed a file (`layer-receipt/1`). An approved element the receipt lists
  as placed, on the claim it still states, carries `in_layer` in the export: the host's
  library and its version. Without a receipt no element carries it.

How to run it with the host application is in [`HANDOFF.md`](HANDOFF.md).
