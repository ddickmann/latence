# R7 — benchmark_integrity-10 — `fuzzy_find`'s exact short-circuit breaks the leftmost contract, so a noisier parse can score better on `order`

**Severity:** major
**Area:** `packages/latence-benchmark/src/latence_benchmark/scoring.py`
**Status:** FIXED

## What is wrong

`fuzzy_find` documents itself as returning "the end index of the **leftmost** occurrence of
`needle` within `max_diffs` edits", and is described in the module docstring as Sellers'
algorithm "short-circuited by an exact `str.find` first" — i.e. the short-circuit is claimed to
be a pure optimisation of the DP.

It is not. `str.find` returns the leftmost **exact** occurrence, which can end *later* than the
leftmost **approximate** occurrence the DP would find:

```python
exact = haystack.find(needle)
if exact != -1:
    return exact + len(needle)   # answers the question instead of bounding it
```

So the value returned depends on whether an exact occurrence exists *anywhere* in the haystack —
including far to the right of a within-budget approximate one.

`UnitTestType.PRESENT` / `ABSENT` only ask *whether* a hit exists, so they are unaffected.
`UnitTestType.ORDER` compares the two indices (`before_end < after_end`), so it is scored on
exactly the value the bug corrupts.

## Failure scenario

Unit level — a later exact hit suppresses the leftmost within-budget hit:

```
fuzzy_find("zzzz aXc zzzzzzzzzzzzzzz abc", "abc", 1)  ->  28   (the exact hit's end)
fuzzy_find("zzzz aXc zzzzzzzzzzzzzzz ---", "abc", 1)  ->  8    (the leftmost hit's end)
```

Removing text from the haystack moves the answer *earlier* — the opposite of a monotone search.

End to end, on a real `order` unit test (`before="Introduction"`, `after="Conclusion"`,
`max_diffs=1`) against a page whose running header repeats "Introduction":

| parser output | pre-fix verdict |
| --- | --- |
| `"Intrpduction ... Conclusion ... Introduction ..."` | **FAILED** |
| `"Intrpduction ... Conclusion ... Intreduction ..."` (one *more* OCR error) | **PASSED** |

Adding OCR damage flips a failing reading-order test to passing, because corrupting the clean
later occurrence is what exposes the earlier within-budget one. That directly contradicts the
harness's own anti-gaming property — stated in `score_document_failure` ("a parser must never be
able to raise its way to a better number") and gated in `test_parse_suite.py` — and `order` is a
scored, published class that dominates the `multi_column` split (884 scored tests on
`docs/BENCHMARKS.md`).

## What to build

Make the exact hit **bound** the Sellers scan instead of answering it:

* `str.find` is a cost-0 occurrence ending at `exact + len(needle)`, so nothing after that index
  can be the leftmost end — run the DP over `haystack[:exact + len(needle)]` and return the first
  end index it finds. The DP is guaranteed to return by that bound (the exact hit itself costs
  0), so the common exact case stays cheap, which is the whole justification for the
  short-circuit.
* `max_diffs <= 0` (no budget) keeps the exact answer directly — with a zero budget the exact hit
  *is* the leftmost occurrence.

The module docstring's claim about the short-circuit is corrected in the same change.

## Published-artifact migration

`fuzzy_find` is inside `_SCORING_BEHAVIOUR`, so the fix moves `ScorerPin.algorithm_digest`
(`ac7b1361a4c999a7` → `a6182621fdc5753c`) and `carry_forward` refuses the published Parse
measurement until the sidecar is updated.

Unlike audit R7-9, this fix **can move published verdicts** — that is the point of it — and the
Parse suite needs olmOCR-bench over the network, so it cannot be re-run in the merge gate. The
digest is therefore updated together with an explicit **run note** on the Parse measurement,
which `render_markdown` publishes on `docs/BENCHMARKS.md`: the counts predate the fix, the
`order` share of the number is the pre-fix scorer's, and the measurement must be re-run with
`latence-benchmark run --suite parse` before it is relied on. Both artifacts are regenerated
through `results.write_results`, so the freshness gate validates them.

## Acceptance criteria

1. A later exact occurrence never changes the value `fuzzy_find` returns for an earlier
   within-budget occurrence (leftmost contract holds).
2. `fuzzy_find` with `max_diffs = 0` is unchanged, and an empty needle still returns 0.
3. Adding OCR damage to a parse cannot flip an `order` verdict from FAILED to PASSED.
4. The scorer fingerprint moves, and `docs/benchmarks/results.json` /
   `docs/BENCHMARKS.md` are regenerated by the real renderers — no hand-edited artifact, and the
   pre-fix provenance of the Parse counts is stated on the published page, not restamped
   silently.
5. No test is weakened or deleted; the fast suite stays green at or above 3320 passed /
   29 skipped.
